# 文章配图

下文的 `pnpm` 命令都必须在配图项目（见「术语」）的根目录运行。

## 术语

- `<skill 目录>`：本文件所在目录。
- 文章：一个 Markdown 文件。文章目录：它所在的目录。
- 配图项目：`<文章目录>/assets/sources/figures/`，由 `<skill 目录>/new-project.sh` 从 `<skill 目录>/template/` 建成，它的 `package.json` 里 `name` 是 `article-figures`。
- 配图：配图项目出的每一个文件。种类有三种：`still` 静态图（PNG）、`gif` 动图（GIF）、`cover` 封面（PNG）；封面以外的叫正文配图。
- 清单：配图的列表，一行一个配图，列为 File、Section、Kind、Title、Shows、Alt text；用户同意的清单存在配图项目根目录的 `figures.md` 里。
- 色系：`src/theme.ts` 里 `HUES` 的一族颜色，框按职责选用。
- 路径颜色：`src/theme.ts` 里 `TONES` 的 `teal`、`orange`、`violet`，用来标出要讲解的路径。
- 步骤：动图 `steps` 里的一项，点亮图里的一部分框和连线。

## 入口

必须先按下表判断从哪里开始。

| 情形 | 判据 | 做法 |
|---|---|---|
| 新配图 | 文章目录下没有 `assets/sources/figures/`，或它是空目录 | 从第 1 步开始 |
| 修改或接着做 | `assets/sources/figures/` 是配图项目 | 读 `figures.md`；清单要变的，按第 2 步第 3 条办；不变的，从受影响或未完成的那一步做起 |
| 平台拒收了一个 GIF | 用户说发布平台拒收了某个动图 | 按第 6 步 |
| 其他 | `assets/sources/figures/` 不空，又不是配图项目 | 不得往里写任何文件，停下问用户怎么办 |

## 两道确认门

1. **清单确认门**：用户明确同意清单之前，只准读文章、查看文章目录、按「本机与网络」确认本机环境和提问，不得运行 `new-project.sh`、写任何文件或画图。判据：说得出用户同意的是哪句话。
2. **预览确认门**：用户明确同意第 4 步发出的预览之前，不得运行 `pnpm deliver`，也不得用任何方式把 `out/` 里的文件复制进文章。判据：说得出用户同意的是哪句话，且那句话之后没有再运行过 `pnpm render`；运行过的，必须重走第 4 步，发出新预览、得到新的同意。

## 制作流程

必须按下列步骤的顺序执行，其余各节的条文在相关步骤必须遵守。`new-project.sh`、`pnpm fonts`、`pnpm render` 报网络错误时必须重新运行，连续三次失败必须停下告诉用户。

### 第 1 步：提出清单

1. 必须读完文章，再定配图：每张正文配图必须对应文章里一段讲结构、流程、状态或先后顺序的文字，说不出对应哪一段的不得列入。
2. 文字的要点在于先后顺序的，必须做成动图；其余做成静态图。
3. 必须把清单按 `figures.md` 的列发给用户：正文配图每行写文件名、所属节、种类、英文标题、画什么、建议的 alt 文字；封面一行的「画什么」写英文副标题和简图画什么。
4. 文件名必须是小写字母、数字和单个连字符组成的名字加扩展名，`still` 与 `cover` 用 `.png`，`gif` 用 `.gif`；名字即配图的 `id`。
5. alt 文字必须用文章的语言写：中文文章写中文，英文文章写英文。
6. 用户要改的，改完重发，直到用户明确同意。

### 第 2 步：建项目

1. 必须运行 `<skill 目录>/new-project.sh <文章的 Markdown 文件>`。它报 `already holds a figures project` 时，在那个项目里接着做；报 `not empty` 时，按「入口」表最后一行办；报其他错误、又不是网络错误的，必须把报错发给用户并停下。
2. 必须把用户同意的清单写进 `figures.md`，替换模板里的样例表；上下文被压缩后必须以 `figures.md` 为准，不得凭记忆。
3. 清单同意之后，要加图、删图或改清单里的任何一格时，必须先把改后的清单发给用户，用户同意后才能改 `figures.md` 和图。

### 第 3 步：画图

1. 动手画图前必须调用 `/diagram-design` 并遵循其全部规范，再按「图片要求」写 `src/data/figures.ts`。
2. 图里的每条事实都必须能在文章里找到出处。

### 第 4 步：自查并发预览

1. 必须依次运行 `pnpm fonts`、`pnpm check`、`pnpm render`，三条的退出码都是 0 才能发预览。`pnpm render` 报的问题必须改图修掉，不得改 `src/`（`src/data/` 除外）和 `scripts/` 的文件去绕过：`pnpm check` 会比对它们与建项目时的模板。
2. 必须亲自看 `out/` 里的每个 PNG，以及 `out/frames/` 里每个动图每一步和最后停留的画面，对照清单逐项判断 `pnpm render` 量不了的条目：每个框的职责和色系是否按「配色要求」对应；点明框自身身份的词是否写成 `title` 或 `key`；同一事物在框、连线、图例里是否同色；同类连线是否同一种走法；封面的简图是否是设计稿而不是插画。发现问题必须回第 3 步。
3. 必须把下列内容一次发给用户：每个配图文件的绝对路径（含封面）；每个动图每个量过的状态的静帧的绝对路径，即 `pnpm render` 在该动图那一行下列出的文件；`pnpm render` 为每个文件输出的那一行，即尺寸、大小、动图的帧数和一遍的秒数，以及量过哪些状态；它最后的 `ALL PASSED` 一行，即量过的状态都没有问题；上一条逐项判断的结论，并写明这几条没有测量，原因是只能凭职责和含义判断。
4. 用户提出修改时，必须回到受影响的那一步改完，再重新走到本步。

### 第 5 步：放进文章

1. 用户明确同意预览后，必须运行 `pnpm deliver`。它报 `run pnpm render` 时不得绕过，必须回第 4 步；报其他错误的，必须把它的全部输出发给用户并停下。
2. 必须把 `pnpm deliver` 的输出转告用户：每个文件名、所属节、建议的 alt 文字，以及为保留旧文件而改了名的文件。
3. 不得修改文章的 Markdown 文件，也不得创建或更新任何发布平台的草稿：把图插进文章、更新草稿由用户另行安排。

### 第 6 步：缩小被拒收的 GIF

1. 用户说平台拒收了某个动图时，必须只调低它的 `fps`，或缩短它的 `stepSeconds`、`holdSeconds`，宽度保持 1080 不变；不得为此删减步骤，删减步骤属于改清单，按第 2 步第 3 条办。
2. 改完必须从第 4 步重新走。

## 图片要求

1. 每个配图在 `src/data/figures.ts` 的 `FIGURES` 里写一项：`id` 与清单的文件名去掉扩展名相同，`kind` 与清单的种类相同，`title` 与清单的英文标题相同。判据：`pnpm render` 核对这三项，不一致即报错停下。
2. 封面必须写 `subtitle`，是一句英文；封面的图必须是只由框和连线组成、画文章主题的简图，不得画成插画。判据：第 4 步亲自看。
3. 图里的一切文字必须是英文。判据：`pnpm render` 报 `not English` 即违反。
4. 字段必须符合 `src/map/geometry.ts` 的 `Figure` 和 `Diagram` 类型。判据：`pnpm check`。
5. 图的坐标单位是配图的设计像素：配图宽 720，静态图按 3 倍出成 2160 像素宽，动图按 1.5 倍出成 1080 像素宽。`view` 的宽不得超过 672，必须框住全部的框、连线和文字。判据：`pnpm render` 报 `room for 672` 或 `outside the diagram's view` 即违反。
6. 框里点明这个框自身身份的词（模块名、类型名）必须写成 `title` 或带 `key: true` 的行。
7. 嵌在大框里的框必须加 `nested: true`，灰色背景分组必须用 `bands`，列标题必须用 `notes`，共用一条线的某个分支要走光点时必须在 `routes` 里单列。
8. 静态图和动图必须有 `legend`，列出图里用到的每种路径颜色和除 `gray` 外的每种色系；封面不放图例。判据：`pnpm render` 报 `legend` 即违反。
9. 连线和 `routes` 的 `d` 只能用大写的 M、L、H、V。判据：`pnpm render` 报 `only M, L, H and V` 即违反。
10. 动图的每一步必须写 `n`（点亮的框）、`e`（点亮的连线，至少一条）和 `at`（步骤序号的坐标，放在点亮的连线旁边）；光点默认走 `e` 里的每条连线，要走别的路线时写 `flows`。判据：`pnpm render` 报 `step` 即违反。
11. 动图一遍不得超过 12 秒：默认每步 1.6 秒、最后停留 2 秒，所以最多 6 步。步骤多于此的，必须拆成两张图或减少步骤，并按第 2 步第 3 条先改清单。判据：`pnpm render` 报 `over 12 s` 即违反。

## 配色要求

1. 色值只准写在 `src/theme.ts`，别处一律引用。判据：`pnpm check`。
2. 框的色系必须按职责从下表选，表外的职责选一个没用过的色系，职责多于 7 种时必须停下问用户：

| 色系 | 职责 |
|---|---|
| `blue` | 外部系统 |
| `teal` | 程序层：由程序确定性处理，如入口、过滤、查表 |
| `amber` | 决策层：由模型判断和调度 |
| `green` | 执行层 |
| `violet` | 控制回路 |
| `pink` | 持久状态 |
| `gray` | 被丢弃或不参与的部分 |

3. 需要讲解的路径必须按类型用路径颜色标出：同一类路径用同一种颜色；类型多于 3 种时只标最需要区分的 3 种，普通连线不标颜色。
4. 同一事物作为普通行（不是所在框自身的身份）或连线标签出现在多处时，这些地方都必须写 `accent`，用同一个颜色；`accent` 不得与 `key` 同用。

## 本机与网络

1. 第 2 步之前必须确认本机有 `node` 和 `pnpm`，缺任一则停下告诉用户，不得自行安装。
2. 不得把图里的文字发给任何在线服务。`pnpm fonts` 只向 Google Fonts 发送英文用到的字符，每个只发一次、按编码排序，不算发送文字。
