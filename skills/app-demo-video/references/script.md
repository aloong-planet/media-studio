# 台本与文字风格

## 叙事骨架

- 必须用“具体场景 → 问题变得明显 → 产品的核心价值 → 实际操作证明 → 使用边界 → 一个行动”组织内容。必须以观众的任务作为选取功能的依据；功能不能帮助完成该任务时，应删去或压缩为补充镜头。
- 必须把核心价值写成一句可被演示验证的判断，例如“把分散的工作重新接起来”；不得只写“高效、智能、强大”而没有操作结果。
- 开头必须让观众先认识自己的处境，再看到 app。必须选一个日常动作，展示次数或对象逐渐增多、产生寻找或判断困难，再提出一至两个具体问题；不得把产品首页截图当作建立问题的替代品。
- 演示必须走一条可完成的路径，例如“记得一个问题 → 搜索 → 定位内容 → 查看过程 → 继续工作”。必须用前一个结果引出后一个动作，不得用章节标题之间的长空白代替衔接。
- 结尾必须写明真实可用范围和一个下一步；处于预发布阶段时必须使用准确的 beta / pre-release 表述。不得制造尚未存在的下载、跨平台支持或自动化能力。

## 可朗读的语言

- 旁白必须使用完整、连贯的口语段落，用连接词表达时间、因果和转折；不得把短标题串成“One task. Another task. More work.”式碎句。英文必须采用自然缩写和直接称呼，中文必须按中文表达重新组织，不得逐字翻译英文语序。
- 屏幕文字必须提炼关键词或问题，旁白必须补足语境；同一段不得同时要求观众读长文案和听不同的长句。必须把 `spoken`、`screenText` 和 `caption` 分开记录，防止发音替换污染屏幕上的正式名称。
- 问句必须有前文铺垫、具体对象和自然连接；不得通过每个词之间加停顿或夸张标点制造疑问。必须将重音标在意义变化处，例如“哪个项目”“哪一次会话”，而不是所有名词都强调。
- 必须在台本阶段朗读检查：每句是否能一口气理解、代词是否有明确对象、前后句是否连贯、画面能否证明所说的事。必须把过长句拆成完整语义单位，不能机械地按字幕行数切配音。

## 台本审核模板

必须用下列表格组织待审核版本；完整旁白必须保留为段落，预计时长不得伪装成已测量时长。

| 段落 ID | 目的 / 观众的问题 | 完整旁白 | 屏幕短文案 | 画面意图 / 产品证据 | 预计时长 |
|---|---|---|---|---|---|
| opening | 建立处境与困难 | 连贯讲述问题产生的过程 | 一至两个问题 | 情景示意，不展示 app | 预计值 |
| reveal | 提出核心价值 | 自然引出 app | app 名称与收益 | 品牌到真实界面 | 预计值 |
| task | 用操作证明价值 | 动作、结果及下一步的连接 | 必要的定位词 | 实际操作路径 | 预计值 |
| close | 说明边界并邀请尝试 | 一句总结与一个行动 | 发布状态与入口 | 收束画面 | 预计值 |

必须把 `task` 按真实任务的必要步骤展开；模板行数不得决定镜头数或配音次数。

## 介绍文章与视频说明

- 必须以创作者真实动机开头，接具体困扰、两至三个可验证用途、工作方式与边界、当前阶段和反馈邀请，最后给演示及入口。不是创作者本人已确认的经历，不得写成第一人称事实。
- 必须保持文章、旁白、屏幕承诺和实际产品版本一致；文章可以解释视频容不下的背景，但不得新增未经查证的产品能力。
